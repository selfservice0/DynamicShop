# DynamicShop 3.0 website

This directory contains the production website source. It uses the plugin's live API; the separate GitHub Pages demo remains a local-data demonstration.

Run `node web-src/build.cjs` from the repository root after editing these files. Commit the generated files in `src/main/resources/web/` too. Maven packages those generated files, so building the plugin does not require Node.js. Maven replaces only explicit @project.version@ markers; JavaScript ${...} expressions must remain untouched. The user-facing version for this release is **v3.0.2**, and the plugin version is **3.0.2**.

## Upgrading an existing server

Install the new JAR and restart the server. Existing web files are retained by default. Administrators with `dynamicshop.admin` (operators by default) are notified on joining if the bundled website is newer.

- `/shopadmin webupdate check` checks the installed files.
- `/shopadmin webupdate` backs up and installs all bundled web files. It also works from the console.
- The new website provides **Administration → Actions → Update website files**.
- When old web files are installed, `/admin.html` serves a standalone upgrade screen. Sign in with an existing web admin account, or open the link generated by `/shopadmin webadmin`. Its “Continue to the existing admin page” link preserves access to the old interface.

Each update backs up replaced files in `plugins/DynamicShop/web-backups/`, outside the served `web/` directory. It replaces bundled HTML, CSS and JavaScript, including custom edits to those files. Shop data, web admin accounts and `website-appearance.json` are kept. Additional files are left alone. Updates install files from the installed JAR, without downloading or updating the plugin itself.

`webserver.force-update-files: true` performs the same backup and replacement on every startup. Its default is false. Web admin updates require administrator authentication and `webserver.admin-enabled: true`.

## Server data and settings

The catalog shows current server stock and prices. Item graphs use the per-item prices of actual recorded trades. Market activity offers Last day, Last week and Forever; Forever covers all transactions currently retained in memory, limited by `logging.max_recent_transactions`, rather than the complete disk archive. Purchases and sales still happen in Minecraft.

Six designs are available: Classic, Market Hall, Inventory, Nova, Chest GUI and DSX Exchange. DSX uses the shared catalog, filtering, watchlist and item history, presented as a quote board with ask/bid prices and recorded trade activity. Eight color palettes and twelve accent presets are available for every design. Administrators save the shared design, colors, fonts, branding and Home URL to `website-appearance.json`. Each visitor's watchlist stays in that browser's local storage. Only authenticated administrators can change server settings.

## Verification

### Optional aggregate website metrics

`webserver.usage-metrics` defaults to true. The administrator can disable **Share website usage counts** in Administration → Configuration, or set the config flag false and reload. This stops accepting usage events and discards pending counters. Disabling bStats globally in `plugins/bStats/config.yml` before server startup also disables website collection. Existing bStats plugin metrics are separate from the new website switch.

Every visitor has a **Usage privacy** footer control to opt out for their browser and this website. Do Not Track and Global Privacy Control signals also disable collection. No visitor identifiers or event history are stored; only four in-memory aggregate counters are sent via the existing bStats integration. The requests contain only an allowlisted event name, never search text, item names, players, account information, query strings, or form values. Browser visitors contact the Minecraft server, not bStats. Counts are best-effort (not unique users): reloads can count again, automated requests can inflate them, and server restarts or failed submissions can lose unsent counts. The endpoint accepts at most 1,000 events per minute per server without identifying visitors.

The bStats project owner must register these custom charts on project **28506** for them to appear:

| Chart ID | Type | Meaning |
| --- | --- | --- |
| `website_page_view` | Single line | Page views since the previous metrics submission |
| `website_item_open` | Single line | Item detail opens since the previous submission |
| `website_search` | Single line | Search interactions after a one-second pause |
| `website_watchlist_change` | Single line | Watchlist additions/removals since the previous submission |
| `website_design` | Simple pie | Selected design on reporting servers |

Chart setup: https://bstats.org/docs/custom-charts. The website opt-out controls do not remove anonymous totals already submitted, nor do they disable unrelated server or reverse-proxy access logs.

`mvn test` includes website appearance validation, safe file replacement and backup tests, and an HTTP test proving unauthorized requests cannot reach mutation handlers. `checks/mock-server.cjs` is a localhost-only API fixture for browser testing (`node web-src/checks/mock-server.cjs`, port 8791, after running Maven; it serves target/classes/web). Pass a port and web directory as arguments to test files extracted from the JAR. Its sample data, test credentials and request journal are not packaged into the JAR. Browser fixture checks do not replace testing on a running Minecraft server.
